## 0. 现状 · 当前 v1 方案（已上线）

### 0.1 当前实现：规则引擎 v1（加权随机 Weighted Random）

文件：[douke.html#L293-L360](file:///workspace/douke.html#L293-L360)

**推荐流程**：
```
候选池过滤 → 8 项权重相乘 → 加权随机抽取
   ↓
权重规则：
  w *= 0.05   1 小时内已看过（新鲜度）
  w *= 0.3    最近 5 张 ≥2 同科目（科目轮换）
  w *= 1.4    难度自适应（简单题正确率<40% / 难题正确率>70%）
  w *= 1.1    中等题默认加权
  w *= 0.4    最近 3 张 ≥2 同类型（类型多样）
  w *= 0.3    已收藏题目（不想重复）
  w *= 1+w/200 考试权重越高优先级越高
  w *= 2~0.1  进度卡按间隔触发
  w *= 0.6~1.3 题目质量分（DoukeScoring 质量闭环）
  w *= 0.5~1.2 用户行为反馈分（DoukeScoring 行为闭环）
```

### 0.2 现状优势 & 劣势

| 维度 | 现状（规则 v1）|
|---|---|
| 上线速度 | ✅ 极快，已落地 |
| 可解释性 | ✅ 每一条权重都能解释原因 |
| 无数据依赖 | ✅ 0 用户数据也能跑 |
| 计算成本 | ✅ O(N)，浏览器端 JS 即可 |
| 个性化深度 | ❌ 只能做"粗粒度适配"，无法理解个体差异 |
| 参数调优 | ❌ 8 个参数靠拍脑袋，网格搜索虽然可用但不可持续 |
| 冷启动新题 | ❌ 新题目因无历史行为分，长期被低质量题挤掉（除非 score 元数据极高）|
| 长期学习轨迹 | ❌ 没有"先学 A 再学 B"的前置依赖概念 |
| 用户间差异化 | ❌ 两个零基础新用户看到的内容几乎一样 |

## 1. 候选方案全景（6 大流派）

抖科推荐算法的设计空间很大，我们整理了 6 类主流方案，每类对应抖科不同阶段：

---

### 方案 A · 规则引擎系列（Rule-based + 衍生）

**适用阶段**：v1.0 ~ v5.0（0-100 用户，0-2k 题库）

| 子方案 | 做法 | 适用场景 |
|---|---|---|
| A1 手工规则 | 当前 v1（8 条硬规则）| MVP 起步、验证产品形态 |
| A2 自动调优规则 | v3 规划：网格搜索 + 爬山法 + 模拟退火，在 200 次仿真会话中找最优参数集 Θ | 规则体系不变，但参数从人工改为仿真寻优 |
| A3 ELO 画像规则 | v3.5 规划：每个学科+难度维护用户能力值 ELO(θ)，题目难度匹配 θ±0.5σ | 用户画像从"正确率"升级为"能力估计" |
| A4 多臂老虎机（MAB）| UCB / Thompson Sampling，把每类卡片/每个 topic 当一个臂，按收益（正确率+dwell）动态分配曝光 | 新题冷启动 + topic 间流量分配 |

**推荐度**：⭐⭐⭐⭐⭐（现阶段最优）

**承载力要求**：
- 纯浏览器端：无需后端，localStorage 存 500 条记录
- 后端聚合：Vercel KV（1GB = 百万级记录，免费额度可用）

---

### 方案 B · 统计学习模型（Statistical Models）

**适用阶段**：v6.0 ~ v10.0（100-1万用户，2k-1万题库）

| 子方案 | 做法 | 解决痛点 |
|---|---|---|
| B1 逻辑回归（LR）| 特征 X = {用户7信号+题目5元数据+上下文}，y = P(用户答对这题且给好评) | 替代手工权重，特征权重由数据学习 |
| B2 因子分解机（FM）| 二阶特征自动交叉，学习"喜欢AP微积分的用户→大概率喜欢IB Math HL"这类跨域关联 | 用户和题目的稀疏高维特征互动 |
| B3 Item-CF（物品协同过滤）| 算题与题的相似度（共现率），做"做对 A 的 80% 用户也做对 B" | 题目之间的关联推荐 |
| B4 User-CF（用户协同过滤）| 找和你做过类似行为的 k 个邻居，推他们喜欢你没做过的 | 人以群分的个性化 |

**推荐度**：⭐⭐⭐⭐（v6 必做，性价比最高）

**承载力要求**：
- 算力：LR/FM 训练 1 次 = 几万条记录约 1-10 秒（Node.js 本地脚本即可，不需要 GPU）
- 存储：模型参数是一个 JSON（几十 KB），存 GitHub 仓库或 Vercel KV
- 推理：纯前向 O(特征数)，可编译到浏览器端 JS，无后端负担

---

### 方案 C · 知识图谱 + 路径规划（Knowledge Graph + Planning）

**适用阶段**：v11.0 ~ v15.0（体系成熟期）

| 子方案 | 做法 | 解决痛点 |
|---|---|---|
| C1 前置依赖图 | 把 308 门课程+4400+知识点建成 DAG：线性代数→微积分→机器学习 | 解决"先学 A 再学 B"的顺序问题 |
| C2 BFS/DFS 路径推荐 | 从用户当前掌握节点出发，给下一张卡片选"入边都已满足"的候选 | 保证学习路径不跳步 |
| C3 SRS（间隔重复）| Ebbinghaus / SM-2，错题/知识点按 T+1/T+3/T+7 到期自动回放 | 记忆曲线不遗忘 |
| C4 Dijkstra 最短路径 | 把学习路径当图搜索，边权重=预计耗时+失败率，求到目标的最小代价路径 | 用户想"3个月从IGCSE进阶到AP微积分"这类目标 |

**推荐度**：⭐⭐⭐⭐（v11+ 必做，和 prereq 板块打通）

**承载力要求**：
- 图数据库：Dgraph / Neo4j Aura（免费版 1 万节点够用），或用 JSON + 前端遍历（DAG 不深）
- 路径搜索：单次 Dijkstra 微秒级，浏览器端即可

---

### 方案 D · 深度学习（Deep Learning）

**适用阶段**：v21.0 ~ v30.0（万级用户+10 万题库之后）

| 子方案 | 做法 | 解决痛点 |
|---|---|---|
| D1 序列推荐（RNN/Transformer）| 把用户 30 张卡片的行为序列当 sentence，预测下一张（类似 GPT 下一 token）| 捕捉长期模式（连错 3 道导数题→下一步推导数入门复习卡）|
| D2 双塔模型（Two-Tower）| 独立 User-Encoder + Item-Encoder，线上算 embedding 点积 | 大规模候选集（>10 万题）毫秒级召回 |
| D3 多模态 + LLM | 用户行为→LLM 生成"诊断卡" + 个性化微建议 | 可解释性和"学习伙伴感" |

**推荐度**：⭐⭐（过早，先做 ABC 再说）

**承载力要求（关键）**：
- 训练：GPU 服务器（4090×1 约 1.5 万/台，或 Lambda Labs 0.5-2 美元/小时 spot 实例）
- 推理：双塔 embedding 可离线算出放 CDN；LLM 需要 API Key（见下一章 Token 需求）

---

### 方案 E · 因果推断 + 学习科学（Causal + Learning Science）

**适用阶段**：v31+（打磨版，做差异化壁垒）

| 子方案 | 做法 |
|---|---|
| E1 Uplift Modeling | A/B 实验中识别"哪种策略对哪类用户真的有用"（去除选择偏差） |
| E2 BKT（贝叶斯知识追踪）| 每道题维护 P(掌握)→P(学会)→P(遗忘)→P(猜对) 四参数隐马尔可夫 |
| E3 难度曲线拟合（IRT 项目反应理论）| 题目三参数：难度 b、区分度 a、猜测 c → 建立人-题二维矩阵 |

**推荐度**：⭐⭐⭐（v10 阶段的 B2+B3 已经部分包含，v30+ 再系统化）

---

### 方案 F · 商业第三方集成（Buy not Build）

| 产品 | 费用 | 适合与否 |
|---|---|---|
| Algolia Recommend | 起价 1 美元/1000 次推荐 + 月费 | ⚠️ 对我们规模太贵，且定制性差 |

**推荐度**：⭐（现阶段不需要，自研 ABC 足矣）

## 2. 方案选型结论（待确认）

### 2.1 阶段路线总览

| 阶段 | 版本 | 方案组合 | 核心原则 |
|---|---|---|---|
| **I MVP** | v1.0 ~ v5.0 | **A1 + A2 + A3 + A4** | 规则体系，纯前端可跑，零后端依赖 |
| **II 数据驱动** | v6.0 ~ v10.0 | **B1 LR + B3 Item-CF + A4 MAB** | 规则之上叠加 LR 模型 rerank |
| **III 体系化** | v11.0 ~ v15.0 | **C1 DAG + C3 SRS + B2 FM** | 知识图谱和统计模型融合 |
| **IV 个性化** | v16.0 ~ v20.0 | **(B4 User-CF) + C4 Dijkstra + E2 BKT** | 冷启动完善，个体画像成型 |
| **V AI 原生** | v21.0 ~ v50.0 | **D1 Transformer + D3 LLM + E1 Uplift** | 序列推荐 + 学习伙伴 |

### 2.2 当前（v1.1）立刻可做的提升

| 提升项 | 怎么改 | 预期收益 | 工作量 |
|---|---|---|---|
| ① 参数 Θ 自动寻优 | 按 DOUKE-ENGINE v3 规划写 1 个 `optimize.js` 脚本，200 会话×50 卡仿真，爬山法 + 模拟退火寻 Θ* | 推荐效果分 +8 ~ +12 分（仿真） | 0.5 天 |
| ② 新题冷启动 MAB | 新题前 3 次曝光强制 Thompson Sampling，不用 score 分 | 新题冷启动 +30% 曝光公平度 | 0.3 天 |
| ③ 题目相似度 Item-CF 雏形 | 做一张 400×400 的 co-occurrence 矩阵，行为≥2 条的用户贡献一次，先 Top-K 存好 | "连续做 A 题→下一步高概率做和 A 相似题" | 0.5 天 |
| ④ profile.accuracy 从 subject.difficulty 升级到 topicCode 粒度 | 当前正确率只到 "sat.easy"，细分到 "sat.M-Alg-1a" | 难度自适应精度↑ | 0.2 天 |
| ⑤ DoukeScoring.records 云同步（Vercel KV）| 答题记录从 localStorage 备份到服务端 kv | 用户换机不丢数据，仿真有真实样本 | 0.3 天 |

## 3. 并行 A/B 框架

多个方案并行测试，核心是 `DoukeScoring.simulateAB()`（已实现）+ 真实小流量实验（待实现）：

```
真实用户 1% 流量 → 随机分流：
  Group A: A1 手工规则 baseline（当前）
  Group B: A2 自动调参规则
  Group C: B1 LR（模型离线训练好后加载）
  Group D: A2 + B3 Item-CF 混合
→ 每组结束后 DoukeScoring 出 5 维报告
→ 胜出方案合并进下一个版本
```

A/B 平台选型：
- v1 ~ v5：自建 DoukeScoring（localStorage 聚合，免费）
- v6 ~ v20：GrowthBook 自托管（MIT 协议，免费，放 Vercel 即可）或 Statsig（免费额度 100 万 MAU）
