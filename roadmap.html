技术方案讨论

🔌 数据层：Supabase Database vs Vercel KV

现状：已有 Supabase Auth 和 Vercel KV（统计用）

Supabase Database 方案
  • 关系型数据，适合复杂查询
  • RLS 行级安全，数据隔离
  • 与已有 Auth 无缝集成
  • 支持实时订阅
Vercel KV 方案
  • Redis 速度快
  • 与现有统计代码复用
  • 但不适合复杂关系数据
  • 查询能力有限

推荐：用户数据用 Supabase Database，KV 继续存访问统计。两套各尽其职。

📅 截止日期提醒实现方案

  • 方案 A：浏览器 Notification API + Service Worker 定时检查（纯前端，无需后端）
  • 方案 B：Vercel Cron Job + 邮件推送（需要用户邮箱，用 Resend / SendGrid）
  • 方案 C：Web Push Notification（VAPID 协议，可离线推送）

推荐：先做方案 A（零成本），后续迭代加方案 C。邮件提醒作为高优先级功能单独评估。

技术方案讨论

💬 评论系统选型

Giscus (GitHub Discussions)
  • 零后端，开箱即用
  • GitHub 账号体系
  • 支持深色模式
  • 无广告，开源
自建评论系统
  • 完全可控，可定制
  • 与站内账号体系打通
  • 开发成本高
  • 需要反垃圾机制

推荐：第一阶段用 Giscus 快速上线，验证需求。用户量起来后再考虑自建。

🛡️ 内容审核方案

  • 前置审核：新用户首帖需审核（人工 + 关键词过滤）
  • 自动审核：接入第三方内容审核 API（如阿里云内容安全、腾讯云内容安全）
  • 用户举报：每帖带举报按钮，社区共治
  • 成本预估：第三方 API 约 ¥0.002/次，1 万条内容 ¥20，早期可接受

⚡ 富文本编辑器选择

  • TipTap：基于 ProseMirror，现代、轻量、可扩展（推荐）
  • Quill：成熟稳定，生态好，但包体较大
  • Markdown 编辑器：如 EasyMDE，技术向用户友好，但普通用户有门槛

推荐：Markdown 先行（开发成本最低），后续再上 TipTap 富文本。

v22.5.0 Idea

国际竞赛体系 — 常见国际竞赛全收录，按学科分类、难度分级、适合专业推荐，帮助学生找到适合自己的背景提升竞赛。

为什么单独做竞赛板块
  • 背景提升是美本申请的核心环节，竞赛是最主流的背景提升方式之一
  • 竞赛信息分散，学生和家长不知道有哪些、怎么选、什么时候参加
  • 与专业页、学校页可形成强关联（"CS 专业推荐参加哪些竞赛"）
  • SEO 流量入口："xx 竞赛含金量"、"xx 竞赛报名时间" 等长尾词

📄 标准竞赛详情页结构

  1. 基本信息卡片：全称、缩写、主办方、官网、报名时间、比赛时间、参赛费用

  4. 比赛形式：个人/团队、线上/线下、题型、时长、轮次
  5. 难度分级：入门 / 进阶 / 顶级（5 星制）
  6. 含金量评估：藤校认可度、对申请帮助程度
  7. 适合专业：关联专业列表（可跳转专业页）
  8. 获奖率 / 分数线：近年数据（如有）
  9. 备考建议：推荐书籍、网站、备考周期
  10. 相关竞赛：同类型/同难度推荐
  11. 常见问题 FAQ

技术方案讨论

🤖 AI 选校匹配算法

核心思路：基于历史录取数据 + 用户背景特征，计算匹配度。

  • 输入特征：GPA、标化、学校背景、专业方向、科研/实习/竞赛、意向国家/排名
  • 算法选型：
    • 方案 A：规则引擎（权重打分）— 可解释性强，易调优，冷启动友好
    • 方案 B：协同过滤 / 向量检索 — 需要大量用户数据，越用越准
    • 方案 C：LLM 直接生成 — 简单粗暴，但不稳定，成本高

推荐：先方案 A（规则引擎）上线，积累数据后迭代到方案 B。LLM 作为补充，生成自然语言解释。

💰 AI 成本估算

  • gpt-4o-mini：输入 $0.15 / 1M tokens，输出 $0.60 / 1M tokens
  • Claude 3.5 Sonnet：输入 $3 / 1M tokens，输出 $15 / 1M tokens
  • 单次文书润色：约 5k 输入 + 2k 输出 = $0.00195（GPT-4o mini）
  • 1000 次/天：约 $2/天，$60/月，可接受
  • 注意：需要做 rate limit 和用户配额，防止滥用

🔍 推荐系统技术栈

  • 冷启动阶段：基于标签的推荐（专业/学校/文章打 tag，按 tag 关联推荐）
  • 有数据后：
    • 向量相似度：用 embeddings 计算内容相似度（OpenAI text-embedding-3-small）
    • 协同过滤：基于用户行为矩阵分解
  • 存储：pgvector（Postgres 扩展，Supabase 支持）+ 缓存层（KV）

💡 技术选型思考原则

  • 渐进式增强：先做最简单的版本验证需求，再逐步加复杂度
  • 能用 SaaS 绝不自建：评论用 Giscus，邮件用 Resend，搜索用 Algolia，省下来的时间做核心功能
  • 保持静态优先：核心内容页保持纯静态，动态功能通过 JS + API 增强，不影响 SEO 和性能
  • 数据可迁移：尽量用标准协议和格式，避免厂商锁定
  • 成本敏感：免费额度优先，按量付费可控，初期避免大额固定成本
